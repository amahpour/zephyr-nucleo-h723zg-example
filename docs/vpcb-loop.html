At a glance

Which code runs in which process

A conventional simulated board is one program: the firmware asks for a voltage and something in the same binary answers. Here the peripherals are separate executables, so an I²C transfer genuinely leaves the firmware's address space. Every box below is a real file; the horizontal rules are real process boundaries.

The only thing shared across the boundary is vpcb/include/vpcb/proto.h, which compiles into both sides and is allowed to include nothing but <stdint.h>. If that header ever needs a Zephyr header or a host header, the process boundary has leaked.

Two consequences fall straight out of the picture. Killing a chip process makes its address stop acknowledging — the driver gets -19 with no rebuild and no mock. A net is whatever is wired to it right now: the board works each one out from the netlist on demand, so once a chip is gone its nets float, and the firmware reports --- rather than a voltage nobody is driving.

The loop

What happens between dacset 0 2000 and adcregs

The firmware never sees the DAC. It calls the Zephyr DAC API; the dacx578 driver turns that into three bytes on an I²C address, and everything past that address lives in a different program with a different address space. The value only returns because a separate board process holds the netlist that says which DAC channel is soldered to which ADC pin.

Inside the firmware process

Where Zephyr ends and the host begins

The socket call cannot live in ordinary Zephyr code — Zephyr's headers and libc collide with the host's. native_sim resolves this by compiling designated files in a separate host context, so the driver is split in two halves that never share a compilation unit.

The test: chip present, chip absent

Same firmware, same command, one process not started

This is the case a linked-in emulator cannot produce. Because the chip model is a separate program, removing it is not a code change or a mock — you simply don't launch it, and the bus behaves the way copper does when nothing acknowledges.

When the board lies

Three places the truth used to die, and the matrix that checks it no longer does

Cut one trace and the firmware used to print ch[3]: 0 mV — exactly what it prints for a channel genuinely at zero volts. The write succeeded, the chip was fine, the log was silent. The answer to is this reading real? existed at the bottom of the stack and was thrown away three separate times on the way up. Fixing any one layer alone would not have been enough.

Layer 1 vpcb-board The board model
floating net → 0 µV, OK“Undriven net: floating. Model as 0 V for now.” The model had the firmware’s bug.
floating net → UNDRIVENA new status, and no invented voltage. Nets are worked out from the netlist on demand, so a chip that leaves stops driving them.
socket · the answer crosses into the firmware
Layer 2 adc_backend.c QEMU, virtual PCB and hardware alike
log, write 0, return successThe caller could not tell a failed channel from one at 0 V.
per-channel validity flagReturned beside every millivolt value. A failed read, or a net the board says is floating, comes back invalid.
Layer 3 regs.h · adcregs The register file
mv[], seq, timestampNo field for it. Nowhere to put the truth even once every layer below told it.
valid[] beside mv[]Every number carries “is this real?” next to “what is it?” — and adcregs prints ---.

The fault matrix

28 hardware faults injected into one running firmware, with the board put back after each. The board re-reads its netlist on SIGHUP, so a trace is cut or crossed in milliseconds without restarting anything. The rule every case enforces: adcregs shows the right number or ---, never a confident wrong one.

The labels were tested, not asserted. Run against firmware without the three layers, the 19 cases that rely on the board knowing a net is floating all fail — each reports its fault as a confident 0 mV — and the 9 bench-detectable cases still pass.

That split is the honest boundary of this twin. A floating pin is something the virtual board can see and a real ADC cannot, so the twin-only cases will not carry over to the bench. Everything else does: the −19, the crossed wires, the datasheet budget, and every layer passing along “not a real reading” when a read genuinely fails.

On the real board

The virtual board passed everything. The first bench run found what it can’t model.

Same firmware, same tests, on a real NUCLEO-H723ZG with one DAC7578 breakout on twelve jumper wires. Every test passed: the original suite, and a new isolation test that holds all eight channels at different voltages at once. Then a new sweep stepped every channel through 129 voltages, and plotted how far each reading was from what the DAC was told to drive.

The cause: not enough time to charge

Before each conversion, an ADC connects a tiny capacitor to the pin and lets it charge to the pin’s voltage. The firmware asked for the driver’s default sampling window — which, for this ADC, is the shortest one it has. The capacitor never got all the way there. It reads like the safe choice. It isn’t.

── app/targets/hw/adc_backend.c ── - .acquisition_time = ADC_ACQ_TIME_DEFAULT, /* Use driver default */ + .acquisition_time = ADC_ACQ_TIME_MAX,

The firmware converts each channel once every 100 ms, so the longest window costs nothing. A scope probe clipped to A4 made the error smaller, too: the ADC borrowed charge from the probe’s capacitance. The instrument you’d use to check the reading changed it.

Why the twin passed. The virtual board models what a circuit does — which pin connects to which, and what each chip drives — not how long anything takes. The fix lives in a file only the real board builds, so the virtual results could not change, and did not need to.

The tolerance went from 150 mV, sized for an analog switch the rig no longer has, to 50 mV, sized from the DAC’s datasheet and what the bench measured. At 50 mV the same tests fail the old firmware nine times.

A real cut wire

On the virtual board a cut trace reads ---, because the board knows nothing drives the net. Pull A5’s jumper on the bench and the ADC reads a number instead — a floating pin converts to whatever charge is sitting on it. The needle can’t tell. But it can be tested: change what the DAC sends, and a cut input doesn’t follow.

── A5 unplugged at the Nucleo; channels 4, 5 and 6 all set to 2800 mV ── uart:~$ adcregs ch[4]: 2802 mV ch[5]: 281 mV ch[6]: 2797 mV

Every round of the isolation test failed on channel 5, and only channel 5. In one round the floating pin happened to read 224 mV against a 300 mV setpoint — the old 150 mV tolerance would have passed it. walkthroughs/04-real-hardware.md replays all of it on your own bench, one commit at a time.

How it gets built

Two toolchains that never meet, and the header that joins them

The chip models compile with plain host gcc and know nothing about Zephyr — no ZEPHYR_BASE, no devicetree, no west. That is the point: they are reusable against any MCU or RTOS. The only thing shared across the boundary is a protocol header that includes <stdint.h> and nothing else.

Running it

Four processes, started in order

# host side — no Zephyr needed cmake -S vpcb -B build-vpcb && cmake --build build-vpcb # firmware west build -b native_sim app -d build-vpcb-fw # bring up the board, then the chips, then the MCU ./build-vpcb/vpcb-board --sock /tmp/vpcb.sock --netlist vpcb/netlists/adc_loopback.txt & ./build-vpcb/vpcb-dac7578 --sock /tmp/vpcb.sock --addr 0x48 & ./build-vpcb/vpcb-dac7578 --sock /tmp/vpcb.sock --addr 0x4c & ./build-vpcb-fw/zephyr/zephyr.exe # omit the two dac7578 lines to get the chip-absent case

Three things worth remembering

The clock is for pacing, not synchronising. Reactive chip models need no shared clock — a register write is ordered by the request/response itself. But with simulated time free-running, the 100 ms sample period elapses instantly and the ADC floods the board with net reads. CONFIG_NATIVE_SIM_SLOWDOWN_TO_REAL_TIME is in there as a rate limiter.
Include paths don't propagate to the host context. target_sources(native_simulator INTERFACE …) works from an application CMakeLists, but INTERFACE_INCLUDE_DIRECTORIES is not among the properties arch/posix/CMakeLists.txt honours. Include paths for bottom-half files have to be passed as -I through target_compile_options.
The async analog domain is real, and it bites. The first board implementation assumed the next message from a chip would be its reply. It wasn't — the chip drives its output first. The board now services interleaved NET_SET while awaiting a reply, which is the correct model: a chip changes its pins whenever it likes.
